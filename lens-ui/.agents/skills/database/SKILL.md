# Database

Follow [workflow](../workflow/SKILL.md) for discovery, registration and
unresolved decisions, and [backend](../backend/SKILL.md) for the surrounding
service/router conventions. All source paths below are repo-relative.

## Locate the implementation

Start at `llm_d_bench/db/README.md` -- it is the front door for this package
and maps every workflow to the right, more detailed document:

- `llm_d_bench/db/dao/README.md`: reading/writing data from a router, service
  or background job.
- `llm_d_bench/db/migrations/README.md`: adding a column/table, or otherwise
  changing a table's shape.

Do not restore the reverted JSON `Store`/file-based persistence abstraction
for structured data that already has a table. New structured data belongs in
a table with a DAO, following the existing `models/*.py` + `dao/*.py` pattern,
not a new on-disk JSON store.

## Read/write data

Only import `*Dao` classes (`llm_d_bench/db/dao/*.py`) from service/router
code -- never a `*Row` ORM class or a `Session` directly. Each DAO method
opens and closes its own short-lived session and converts to/from the
feature's existing DTO (a Pydantic model or dataclass), so callers never see
ORM state leak across a request or task boundary.

```python
from llm_d_bench.db.dao.storage_volume import StorageVolumeDao
from llm_d_bench.storage.contracts import StorageVolume

dao = StorageVolumeDao()
volume = dao.get(volume_id)
dao.list()
```

See `dao/README.md` for the full method set (`create`/`get`/`list`/`save`/
`delete`), handling `ConcurrentUpdateError`, and nested/related data.

## Schema changes require human review before they are made

Any change to a table's shape -- adding, removing or renaming a column or
table, changing a type, constraint, index or relationship -- is a
schema change and must be reviewed and approved by a human **before** it is
applied. This includes changes an agent judges safe or purely additive.

1. Propose the change (the `models/*.py` edit and its rationale) and pause for
   explicit human approval, following the same handoff discipline as
   [workflow](../workflow/SKILL.md#human-decision-handoff).
2. Only after approval, apply the `models/*.py` edit and generate the Alembic
   revision (`alembic revision --autogenerate -m "..."`).
3. Review the autogenerated script by hand -- autogenerate misses data
   migrations, renames (it emits drop+add), and some constraint changes. See
   `migrations/README.md` for the worked examples (add column, add table, drop
   table) and the pitfalls to check for in every generated script.
4. A schema change is not complete until its migration script exists and has
   been reviewed alongside the model change in the same PR. Do not leave
   `models/*.py` ahead of the latest migration revision.

## Testing

Tests never run Alembic migrations and never talk to a real PostgreSQL
instance. The root `conftest.py` gives every test an isolated, empty in-memory
SQLite database built via `Base.metadata.create_all()` (always reflecting the
current `models/*.py`, independent of migration history) and rebinds the
process-wide engine to it for the test's duration.

## Verify the affected contract

Use `make test-python` (or the narrower `pytest llm_d_bench/db` /
`pytest <domain>` selection) after any DAO or model change. Cover DAO callers
in the owning domain, not just `llm_d_bench/db/`. Report which schema changes
were approved by a human and where that approval is recorded.
