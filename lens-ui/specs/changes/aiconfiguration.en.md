# Configuration Architecture & API Design

## 1. Workflow

The user flow of the Configuration module starts from **Candidate Source**.

After the user selects a Candidate Source, they can see one or more Configuration Files under that Source. They can view, choose, and further modify those configurations. After the user clicks Generate/Confirm, the backend automatically performs Capability Check, Normalize, and Validate; these backend steps do not need to be exposed to users separately.

```text
┌───────────────────────────────┐
│ 1. Select Candidate Source    │
│ AIC / Baseline / PD / EPD     │
│ Tiered Cache / Historical     │
│ Manual                        │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ 2. View Configuration Files   │
│ Show the configuration files under this Source     │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ 3. Select / Edit Config       │
│ Select one or more configuration files         │
│ Users can continue editing the configuration           │
│ Manual: Form / YAML Upload    │
└───────────────┬───────────────┘
                ▼
         User clicks Generate
                │
                ▼
        POST /configurations/resolve
                │
                ▼
┌───────────────────────────────┐
│ Backend Capability Check      │
│ AIC: Model × Hardware         │
│ Not visible to users                    │
└───────────────┬───────────────┘
                │
        Unsupported ──→ Return error
                │ Supported
                ▼
┌───────────────────────────────┐
│ Normalize                     │
│ Normalize fields / structure / defaults      │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ Validate                      │
│ Configuration / resource / compatibility validation      │
└───────────────┬───────────────┘
                │
          Invalid ──→ Return error
                │ Valid
                ▼
┌───────────────────────────────┐
│ CandidateConfig               │
│ type = baseline/pd/epd/...    │
└───────────────┬───────────────┘
                ▼
       POST /configurations/render
                │
                ▼
┌───────────────────────────────┐
│ Render                        │
│ CandidateConfig → deployment structure    │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ Deployable Configuration      │
│ type + format + content       │
└───────────────┬───────────────┘
                ▼
        POST /configurations/save
                │
                ▼
┌───────────────────────────────┐
│ Configuration File            │
│ type + file + metadata        │
└───────────────┬───────────────┘
                ▼
              Deploy
```

### User-visible and backend-internal steps

| Phase | Visible to users? | Description |
|---|---:|---|
| Select Candidate Source | Yes | Select configuration source |
| View Configuration Files | Yes | View existing configurations under this Source |
| Select / Edit Configuration | Yes | Select one or more configurations and edit them |
| Capability Check | No | Backend automatically checks Model × Hardware |
| Normalize | No | Backend normalizes configuration structure |
| Validate | No | Backend validates configuration correctness and compatibility |
| Render | Visible as the result of the generate action | Generate Deployable Configuration |
| Save | Visible as the result of the save action | Save the final Configuration File |

## 2. Candidate Source

### Purpose

The user first selects a configuration source.

| Candidate Source | Description |
|---|---|
| `aic` | Configurations produced by AIC Prediction |
| `baseline_search` | Baseline Search results |
| `pd_search` | PD Search results |
| `epd_search` | EPD Search results |
| `tiered_cache_search` | Tiered Cache Search results |
| `historical` | Historical Results |
| `manual` | User-provided configuration |

> Candidate Source indicates where the configuration comes from; it does not indicate the final deployment type.

Suggested fields:

```yaml
candidate_source:
  name:
  run_id: optional
  result_id: optional
```

## 3. Source Configuration

### Purpose

The concrete configuration files under a Candidate Source.

After selecting a Candidate Source, the user should be able to see the available Configuration Files under that Source and can:

- View configuration content
- Select one or more configurations
- Modify the selected configurations
- Then submit to generate CandidateConfig

### Source Configuration entry points

| Source | Configuration source | User action |
|---|---|---|
| AIC | AIC Prediction results | View / Select / Edit |
| Baseline Search | Configurations generated by Baseline Search | View / Select / Edit |
| PD Search | Configurations generated by PD Search | View / Select / Edit |
| EPD Search | Configurations generated by EPD Search | View / Select / Edit |
| Tiered Cache Search | Configurations generated by Tiered Cache Search | View / Select / Edit |
| Historical | Configurations saved in historical Runs / Results | View / Select / Edit |
| Manual | Form Input / YAML Upload | Create / Edit |

```text
┌──────────────────────────────┐
│ Candidate Source            │
└─────────────┬────────────────┘
              ▼
┌──────────────────────────────┐
│ Available Configuration Files│
│ config-a.yaml               │
│ config-b.yaml               │
│ config-c.yaml               │
└─────────────┬────────────────┘
              ▼
┌──────────────────────────────┐
│ Select Configuration(s)     │
└─────────────┬────────────────┘
              ▼
┌──────────────────────────────┐
│ View / Edit Configuration   │
└─────────────┬────────────────┘
              ▼
      POST /configurations/resolve
```

### Manual Configuration

```text
┌────────────────────────┐
│ Manual Configuration   │
└────────────┬───────────┘
             │
      ┌──────┴───────┐
      ▼              ▼
┌─────────────┐  ┌─────────────┐
│ Form Input  │  │ YAML Upload │
└──────┬──────┘  └──────┬──────┘
       │                │
       └────────┬───────┘
                ▼
┌────────────────────────┐
│ View / Edit Config     │
└────────────┬───────────┘
             ▼
      Resolve Workflow
```

| Mode | Input |
|---|---|
| Form Input | The user fills in `type` and the corresponding parameters in the Lens UI |
| YAML Upload | The user uploads an existing YAML configuration file |

Manual YAML must also go through the subsequent Capability Check / Normalize / Validate.

## 4. Backend Capability Check

### Purpose

After the user clicks Generate, the backend automatically calls AIC before producing CandidateConfig:

```text
Model × Hardware → Supported ?
```

This is a **backend internal step**; users do not need to operate it separately.

```text
┌───────────────────────┐
│ Source Configuration  │
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ Extract Model/Hardware│
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ AIC Capability Check  │
└───────────┬───────────┘
            │
       ┌────┴────┐
       ▼         ▼
 Supported   Unsupported
    │            │
    ▼            └──→ Return reason
 Normalize
```

### Input

Model / Hardware parameters are obtained from Source Configuration or the target Cluster context.

| Parameter | Description |
|---|---|
| `model.id` | Model ID |
| `model.revision` | Optional revision |
| `hardware.accelerator_type` | GPU / XPU, etc. |
| `hardware.accelerator_model` | Actual hardware model |
| `hardware.accelerator_count` | Number of available devices |
| `hardware.accelerator_memory` | Device memory |

### Output

| Field | Description |
|---|---|
| `supported` | Whether Model × Hardware is supported |
| `reason` | Reason not supported |
| `constraints` | Constraints such as TP / replicas / memory |

> Capability Check is no longer an independent Workflow Step in the Lens UI, nor does it need to be exposed as a separately callable user action.

---

## 5. Normalize

### Purpose

Convert different Source Configurations into a unified structure.

| Normalize item | Example |
|---|---|
| Unified field names | `tp`, `tensor_parallel` → `tensor_parallel_size` |
| Unified data types | `"4"` → `4` |
| Fill default values | Default values for optional parameters |
| Source metadata | Store uniformly as `candidate_source` |
| Deployment type | Normalize into top-level `type` |
| topology parameters | serving / encode / prefill / decode / cache |

---

## 6. Validate

### Purpose

Check whether the normalized configuration can continue to Render.

| Validation | What is checked |
|---|---|
| Configuration Validation | Required fields, types, ranges |
| Resource Validation | accelerator count, VRAM, CPU, memory, TP × replicas |
| Compatibility Validation | Model / Hardware / Guide / Cache backend / Feature |

### Type-specific Validation

| `type` | Required configuration |
|---|---|
| `baseline` | serving TP + replicas |
| `pd` | prefill TP/replicas + decode TP/replicas |
| `epd` | encode + prefill + decode |
| `tiered_cache` | serving + cache config |

Output:

```yaml
validation:
  status: valid | valid_with_warnings | invalid
  errors: []
  warnings: []
```

---

## 7. CandidateConfig

### Purpose

The unified standard configuration object inside the Configuration module.

### Core Fields

| Field | Description |
|---|---|
| `schema_version` | CandidateConfig schema version |
| `candidate_source` | Configuration source |
| `type` | Final deployment type |
| `target` | model / cluster / guide |
| `serving` | baseline/tiered serving parameters |
| `encode` | EPD encode parameters |
| `prefill` | PD/EPD prefill parameters |
| `decode` | PD/EPD decode parameters |
| `cache` | tiered cache parameters |
| `resources` | Resource requirements |
| `performance` | predicted/measured performance |
| `validation` | Validation result |

Unified deployment field:

```yaml
type: baseline | pd | epd | tiered_cache
```

Candidate Source is separate from `type`:

```yaml
candidate_source:
  name: aic

type: pd
```

## 9. Deployable Configuration

Deployable Configuration must continue to retain `type`:

```yaml
deployable_configuration:
  type: pd
  format: helm
  content:
    ...
```

Deploy does not need to understand Candidate Source, but it uses `type` to determine the deployment flow:

| `type` | Deploy |
|---|---|
| `baseline` | Baseline deployment |
| `pd` | PD deployment |
| `epd` | EPD deployment |
| `tiered_cache` | Tiered Cache deployment |

# 11. API Design

Since Capability Check is an internal step of `resolve`, Configuration exposes **3 core APIs** to Lens:

| API | Purpose | Input | Backend Process | Output |
|---|---|---|---|---|
| `POST /api/v1/configurations/resolve` | Generate CandidateConfig | Candidate Source + selected/edited Configuration(s) | AIC Capability Check → Normalize → Validate | CandidateConfig(s) |
| `POST /api/v1/configurations/render` | Generate deployment structure | CandidateConfig | Select Renderer → Template → Mapping | Deployable Configuration |
| `POST /api/v1/configurations/save` | Save configuration file | Deployable Configuration | Serialize → Save → Hash | Configuration File |


```yaml
  type:
```
```yaml
  format:
```

```yaml
  name: optional
```

```yaml
  type:
  file_name:
  format:
  path:
  size:
  sha256:
```

```json

    "type": "pd",
    "format": "helm",
```

```json

    "type": "pd",
```

```text

        ↓

        ↓
Execute deployment
```

# 12. Configuration → Deploy Contract

```text
┌─────────────────────────────┐
│ Configuration File          │
│ type: pd                    │
│ format: helm                │
│ path: ...                   │
│ sha256: ...                 │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ Deploy                      │
│ Read type                   │
│      ↓                      │
│ Select deployment workflow  │
│      ↓                      │
│ Load configuration file     │
│      ↓                      │
│ Execute deployment          │
└─────────────────────────────┘
```

Final boundaries:

| Configuration is responsible for | Deploy is responsible for |
|---|---|
| Source config processing | Read the final config file |
| Hidden AIC capability check | Choose deployment type based on `type` |
| Normalize / Validate | Execute Helm/Kustomize/Manifest deployment |
| CandidateConfig | Pod/Service/Endpoint lifecycle |
| Render | Runtime validation |
| Save Configuration File | Teardown / Rollback |
