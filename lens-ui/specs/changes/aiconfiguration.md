# Configuration Architecture & API Design

## 1. Workflow

The Configuration user workflow starts with **Candidate Source**.

After selecting a Candidate Source, users see its Configuration Files. They can view, select, and edit these configurations. On generate/confirm, the backend automatically performs Capability Check, Normalize, and Validate; these internal steps do not need separate user-facing controls.

```text
┌───────────────────────────────┐
│ 1. Select Candidate Source    │
│ AIC / Baseline / PD / EPD     │
│ Tiered Cache / Historical     │
│ Manual                        │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ 2. View Configuration Files   │
│ Show configuration files for the source     │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ 3. Select / Edit Config       │
│ Select one or more configuration files         │
│ Users may edit configurations           │
│ Manual: Form / YAML Upload    │
└───────────────┬───────────────┘
                ▼
         User clicks Generate
                │
                ▼
        POST /configurations/resolve
                │
                ▼
┌───────────────────────────────┐
│ Backend Capability Check      │
│ AIC: Model × Hardware         │
│ Internal backend step                    │
└───────────────┬───────────────┘
                │
        Unsupported ──→ Return error
                │ Supported
                ▼
┌───────────────────────────────┐
│ Normalize                     │
│ Normalize fields / structure / defaults      │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ Validate                      │
│ Validate configuration / resources / compatibility      │
└───────────────┬───────────────┘
                │
          Invalid ──→ Return error
                │ Valid
                ▼
┌───────────────────────────────┐
│ CandidateConfig               │
│ type = baseline/pd/epd/...    │
└───────────────┬───────────────┘
                ▼
       POST /configurations/render
                │
                ▼
┌───────────────────────────────┐
│ Render                        │
│ CandidateConfig → deployment structure    │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ Deployable Configuration      │
│ type + format + content       │
└───────────────┬───────────────┘
                ▼
        POST /configurations/save
                │
                ▼
┌───────────────────────────────┐
│ Configuration File            │
│ type + file + metadata        │
└───────────────┬───────────────┘
                ▼
              Deploy
```

### User-facing and internal backend steps

| Stage | Visible to users | Description |
|---|---:|---|
| Select Candidate Source | Yes | Select configuration source |
| View Configuration Files | Yes | View existing configurations for the source |
| Select / Edit Configuration | Yes | Select and optionally edit one or more configurations |
| Capability Check | No | Backend automatically checks Model × Hardware |
| Normalize | No | Backend normalizes configuration structure |
| Validate | No | Backend validates configuration and compatibility |
| Render | May be shown as the generation result | Generate Deployable Configuration |
| Save | May be shown as the save result | Save the final Configuration File |

## 2. Candidate Source

### Purpose

Users first select a configuration source.

| Candidate Source | Description |
|---|---|
| `aic` | Configuration produced by AIC Prediction |
| `baseline_search` | Baseline Search results |
| `pd_search` | PD Search results |
| `epd_search` | EPD Search results |
| `tiered_cache_search` | Tiered Cache Search results |
| `historical` | Historical Results |
| `manual` | User-provided configuration |

> Candidate Source identifies where a configuration comes from, not the final deployment type.

Suggested fields:

```yaml
candidate_source:
  name:
  run_id: optional
  result_id: optional
```

## 3. Source Configuration

### Purpose

A specific configuration file belonging to the Candidate Source.

After selecting a Candidate Source, users should see its available Configuration Files and be able to:

- View configuration content
- Select one or more configurations
- Edit selected configurations
- Submit to generate CandidateConfig

### Source Configuration entry points

| Source | Configuration source | User action |
|---|---|---|
| AIC | AIC Prediction results | View / Select / Edit |
| Baseline Search | Configurations generated by Baseline Search | View / Select / Edit |
| PD Search | Configurations generated by PD Search | View / Select / Edit |
| EPD Search | Configurations generated by EPD Search | View / Select / Edit |
| Tiered Cache Search | Configurations generated by Tiered Cache Search | View / Select / Edit |
| Historical | Configurations saved in historical Runs / Results | View / Select / Edit |
| Manual | Form Input / YAML Upload | Create / Edit |

```text
┌──────────────────────────────┐
│ Candidate Source            │
└─────────────┬────────────────┘
              ▼
┌──────────────────────────────┐
│ Available Configuration Files│
│ config-a.yaml               │
│ config-b.yaml               │
│ config-c.yaml               │
└─────────────┬────────────────┘
              ▼
┌──────────────────────────────┐
│ Select Configuration(s)     │
└─────────────┬────────────────┘
              ▼
┌──────────────────────────────┐
│ View / Edit Configuration   │
└─────────────┬────────────────┘
              ▼
      POST /configurations/resolve
```

### Manual Configuration

```text
┌────────────────────────┐
│ Manual Configuration   │
└────────────┬───────────┘
             │
      ┌──────┴───────┐
      ▼              ▼
┌─────────────┐  ┌─────────────┐
│ Form Input  │  │ YAML Upload │
└──────┬──────┘  └──────┬──────┘
       │                │
       └────────┬───────┘
                ▼
┌────────────────────────┐
│ View / Edit Config     │
└────────────┬───────────┘
             ▼
      Resolve Workflow
```

| Mode | Input |
|---|---|
| Form Input | Users enter `type` and its parameters in the Lens UI |
| YAML Upload | Users upload an existing YAML configuration file |

Manual YAML must also pass through Capability Check / Normalize / Validate.

## 4. Backend Capability Check

### Purpose

When users generate, the backend automatically calls AIC before producing CandidateConfig:

```text
Model × Hardware → Supported ?
```

This is a **backend internal step** requiring no separate user action.

```text
┌───────────────────────┐
│ Source Configuration  │
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ Extract Model/Hardware│
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ AIC Capability Check  │
└───────────┬───────────┘
            │
       ┌────┴────┐
       ▼         ▼
 Supported   Unsupported
    │            │
    ▼            └──→ Return reason
 Normalize
```

### Input

Model / Hardware parameters come from the Source Configuration or target Cluster context.

| parameters | Description |
|---|---|
| `model.id` | Model ID |
| `model.revision` | Optional revision |
| `hardware.accelerator_type` | GPU / XPU, etc. |
| `hardware.accelerator_model` | Actual hardware model |
| `hardware.accelerator_count` | Available device count |
| `hardware.accelerator_memory` | Device memory |

### Output

| Field | Description |
|---|---|
| `supported` | Whether Model × Hardware is supported |
| `reason` | Reason for lack of support |
| `constraints` | TP / replicas / memory constraints |

> Capability Check is no longer a separate Lens UI Workflow Step and does not require a separate user invocation.

---

## 5. Normalize

### Purpose

Convert different Source Configurations into a consistent structure.

| Normalization | Example |
|---|---|
| Normalize field names | `tp`, `tensor_parallel` → `tensor_parallel_size` |
| Normalize data types | `"4"` → `4` |
| Fill defaults | Defaults for optional parameters |
| Source metadata | Store consistently as `candidate_source` |
| Deployment type | Normalize to top-level `type` |
| topology parameters | serving / encode / prefill / decode / cache |

---

## 6. Validate

### Purpose

Check whether the normalized configuration can proceed to Render.

| Validation | Checks |
|---|---|
| Configuration Validation | Required fields, types, ranges |
| Resource Validation | Accelerator count, device memory, CPU, memory, TP × replicas |
| Compatibility Validation | Model / Hardware / Guide / Cache backend / Feature |

### Type-specific Validation

| `type` | Required configuration |
|---|---|
| `baseline` | serving TP + replicas |
| `pd` | prefill TP/replicas + decode TP/replicas |
| `epd` | encode + prefill + decode |
| `tiered_cache` | serving + cache config |

Output:

```yaml
validation:
  status: valid | valid_with_warnings | invalid
  errors: []
  warnings: []
```

---

## 7. CandidateConfig

### Purpose

The standard internal configuration object used by the Configuration module.

### Core Fields

| Field | Description |
|---|---|
| `schema_version` | CandidateConfig schema version |
| `candidate_source` | Configuration source |
| `type` | Final deployment type |
| `target` | model / cluster / guide |
| `serving` | baseline/tiered serving parameters |
| `encode` | EPD encode parameters |
| `prefill` | PD/EPD prefill parameters |
| `decode` | PD/EPD decode parameters |
| `cache` | tiered cache parameters |
| `resources` | Resource requirements |
| `performance` | predicted/measured performance |
| `validation` | Validation result |

Standard deployment field:

```yaml
type: baseline | pd | epd | tiered_cache
```

Keep Candidate Source separate from `type`:

```yaml
candidate_source:
  name: aic

type: pd
```

## 9. Deployable Configuration

Deployable Configuration must retain `type`:

```yaml
deployable_configuration:
  type: pd
  format: helm
  content:
    ...
```

Deploy does not need to interpret Candidate Source; it selects the deployment workflow using `type`:

| `type` | Deploy |
|---|---|
| `baseline` | Baseline deployment |
| `pd` | PD deployment |
| `epd` | EPD deployment |
| `tiered_cache` | Tiered Cache deployment |

# 11. API Design

Capability Check is internal to `resolve`, so Configuration exposes **three core APIs** to Lens:

| API | Purpose | Input | Backend Process | Output |
|---|---|---|---|---|
| `POST /api/v1/configurations/resolve` | Generate CandidateConfig | Candidate Source + selected/edited Configuration(s) | AIC Capability Check → Normalize → Validate | CandidateConfig(s) |
| `POST /api/v1/configurations/render` | Generate deployment structure | CandidateConfig | Select Renderer → Template → Mapping | Deployable Configuration |
| `POST /api/v1/configurations/save` | Save configuration file | Deployable Configuration | Serialize → Save → Hash | Configuration File |

# 12. Configuration → Deploy Contract

```text
┌─────────────────────────────┐
│ Configuration File          │
│ type: pd                    │
│ format: helm                │
│ path: ...                   │
│ sha256: ...                 │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ Deploy                      │
│ Read type                   │
│      ↓                      │
│ Select deployment workflow  │
│      ↓                      │
│ Load configuration file     │
│      ↓                      │
│ Execute deployment          │
└─────────────────────────────┘
```

Final boundaries:

| Configuration responsibilities | Deploy responsibilities |
|---|---|
| Source config processing | Read the final config file |
| Hidden AIC capability check | Select deployment type using `type` |
| Normalize / Validate | Execute Helm/Kustomize/Manifest deployment |
| CandidateConfig | Pod/Service/Endpoint lifecycle |
| Render | Runtime validation |
| Save Configuration File | Teardown / Rollback |
