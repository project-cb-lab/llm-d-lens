# `llm_d_bench.db` -- the SQLAlchemy data access layer

This package is where every table's structure, storage engine configuration,
and read/write access lives. This README is the front door: it explains how the
pieces fit together and points you at the right, more detailed document for
whatever you're actually trying to do.

```
llm_d_bench/db/
├── base.py          # shared declarative Base, portable column types, DTO<->Row mixin
├── engine.py         # Engine/Session construction (one process-wide engine)
├── settings.py        # external vs. embedded database configuration
├── system_router.py    # "Step 0" -- configures the app's own database at install time
├── models/            # one *Row ORM class per table -- the schema itself
├── dao/                # one *Dao class per table -- read/write access, see dao/README.md
└── migrations/          # Alembic migration scripts, see migrations/README.md
```

## Two things you'll want to do, and where to go for each

| You want to... | Read |
|---|---|
| Read/write data from a router, service, or background job | `llm_d_bench/db/dao/README.md` |
| Add a column/table, or otherwise change a table's shape | `llm_d_bench/db/migrations/README.md` |

The rest of this document is a short map of how the pieces underneath those two
workflows relate to each other, for when you need the bigger picture.

## The four layers

1. **`models/*.py` (`*Row` classes)** -- the actual table definition: SQLAlchemy
   `Mapped[...]`/`mapped_column(...)` declarations, constraints, indexes,
   relationships. This is the single source of truth for the schema. Every
   `*Row` class also declares a `column_map` and mixes in `DeclarativeDtoMixin`
   (from `base.py`), which generates `from_dto`/`to_dto`/`sync_from_dto` for
   free -- the glue that converts between a row and the plain DTO/record type
   the rest of the app already uses (a Pydantic model or dataclass living in
   that feature's own module, e.g. `StorageVolume`, `Cluster`).
2. **`dao/*.py` (`*Dao` classes)** -- one per table, the only thing service-layer
   code should ever import from this package. Each method opens a short-lived
   `Session` (via `BaseDao._transaction()` for writes, `BaseDao._read_only()` for
   reads), does the query/write, converts to/from the DTO, and closes the
   session before returning. See `dao/README.md` for the full guide with
   examples (`create`/`get`/`list`/`save`/`delete`, handling
   `ConcurrentUpdateError`, nested/related data, etc.).
3. **`migrations/versions/*.py`** -- Alembic scripts that evolve a real
   database's schema over time to match whatever `models/*.py` currently says.
   See `migrations/README.md` for the full guide with worked examples (adding a
   column, adding a table, dropping a table) and the pitfalls to check for in
   every autogenerated script before applying it.
4. **`engine.py` / `settings.py` / `system_router.py`** -- infrastructure most
   feature code never touches directly: a single process-wide `Engine` +
   `sessionmaker` (`engine.py`), resolving whether we're talking to an
   external database the user configured or a local embedded PostgreSQL
   instance (`settings.py`), and the one-time "Step 0" setup flow that
   configures which of those two this install uses and builds the initial
   schema (`system_router.py`).

## How a request actually flows through these layers

Using `StorageVolumeDao.create(volume)` as an example:

```
service code:  dao.create(volume)                      # a StorageVolume DTO in
                       │
dao/storage_volume.py: with self._transaction() as session:   # BaseDao opens a Session
                           row = StorageVolumeRow.from_dto(volume)   # DTO -> Row
                           session.add(row); session.flush()
                           return row.to_dto()            # Row -> DTO, session closes here
                       │
service code:  <- a StorageVolume DTO out, fully detached from the DB session
```

Nothing above the DAO layer (routers, services, tests) ever sees a `Session` or
a `*Row` instance -- that boundary is intentional (see "Why a DTO instead of the
ORM row directly?" in `dao/README.md`).

## Quick start

Reading/writing data as a service-layer developer:

```python
from llm_d_bench.db.dao.storage_volume import StorageVolumeDao
from llm_d_bench.storage.contracts import StorageVolume

dao = StorageVolumeDao()
volume = dao.get(volume_id)
dao.list()
```
→ full guide, more DAOs, error handling: `dao/README.md`.

Changing a table's shape:

```bash
# 1. edit the *Row class under models/
# 2. alembic revision --autogenerate -m "..."
# 3. review the generated script
# 4. alembic upgrade head
```
→ full guide, worked examples for add-column/add-table/drop-table:
`migrations/README.md`.

## Testing

Tests never run Alembic migrations and never talk to a real PostgreSQL
instance. The root `conftest.py` gives every test an isolated, empty in-memory
SQLite database (built via `Base.metadata.create_all()`, so it always reflects
whatever `models/*.py` currently says, regardless of migration history) and
rebinds the process-wide engine to it for the duration of that test. This means
DAOs and service code under test always run against a real SQLAlchemy engine,
just not a persistent/external one.
