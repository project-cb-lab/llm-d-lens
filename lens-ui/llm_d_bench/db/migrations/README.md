# Database migrations (Alembic)

This directory is an [Alembic](https://alembic.sqlalchemy.org/) migration
environment for the tables defined under `llm_d_bench/db/models/`. This document
is for developers who are **changing the schema** (adding/removing a column,
adding a table, removing a table, adding an index/constraint, etc.) -- if you
just need to read/write data from service-layer code, see
`llm_d_bench/db/dao/README.md` instead; you don't need Alembic or this directory
for that.

## When you need this

Only when you change (or add/remove) a `*Row` class under `llm_d_bench/db/models/`
in a way that changes the actual table shape in the database, for example:

- adding/removing/renaming a column
- changing a column's type, nullability, or default
- adding/removing an index, unique constraint, or check constraint
- adding a brand-new table (a new `*Row` model module)
- removing a table that's no longer needed

You do **not** need a migration for changes that don't touch the database schema
(e.g. editing a DTO/Pydantic model's business-logic-only fields that are stored
inside an existing JSON column such as `extra`).

## Why this exists (and why `create_all()` isn't enough here)

`Base.metadata.create_all(engine)` (used by the test suite, see root
`conftest.py`) can only create tables that don't exist yet -- it never alters or
drops an existing table, so it's unsuitable for evolving a real, already-populated
database. Alembic tracks schema history as an ordered chain of migration scripts
under `versions/`, and the target database itself remembers which revision it's
on in a small `alembic_version` table -- that's what lets `alembic upgrade head`
figure out exactly which incremental changes still need to be applied.

The very first schema (when the database feature was introduced) was created
directly via `create_all()` and then given a single empty "baseline" migration
(`versions/d54cf30d823b_baseline.py`, stamped rather than executed) purely so
Alembic would have a starting point to diff future changes against. Every
migration from here on is a normal, real Alembic migration, generated the same
way as the worked examples below.

## The general workflow

1. Change the `*Row` class(es) under `llm_d_bench/db/models/` as needed (see the
   three worked examples below for the exact edits each kind of change needs).
2. Generate a migration by diffing your updated models against a database that's
   still on the previous schema:

   ```bash
   alembic revision --autogenerate -m "add priority column to simulation_tasks"
   ```

   This connects to whatever database `llm_d_bench.db.settings.DatabaseSettings`
   resolves to (same env vars the app itself uses --
   `LLM_D_BENCH_DB_MODE`/`LLM_D_BENCH_DATABASE_URL`/etc.), reflects its current
   structure, diffs it against `Base.metadata`, and writes a new script under
   `versions/`.
3. **Always open and review the generated script before applying it** -- see
   "Things autogenerate gets wrong" below.
4. Apply it:

   ```bash
   alembic upgrade head
   ```

5. Commit the generated script under `versions/` along with your model change,
   in the same PR/commit.

The rest of this document walks through the three concrete scenarios you'll hit
in practice, with real generated output for each.

## Worked example 1: adding a column to an existing table

Say you need to add a `priority` column to `simulation_tasks`. Edit the `*Row`
class in `llm_d_bench/db/models/simulation_task.py`:

```python
status: Mapped[str] = mapped_column(String(16), nullable=False)
priority: Mapped[int | None] = mapped_column(Integer, nullable=True)  # new
endpoint_mode: Mapped[str] = mapped_column(String(16), nullable=False, default="external")
```

Then generate the migration:

```bash
alembic revision --autogenerate -m "add priority to simulation tasks"
```

This produces (verbatim, from an actual run against this exact change):

```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column("simulation_tasks", sa.Column("priority", sa.Integer(), nullable=True))
    # ### end Alembic commands ###


def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_column("simulation_tasks", "priority")
    # ### end Alembic commands ###
```

For a nullable column with no default, this is already correct as-is. Two things
to double check before applying:

- If you'd made the column **`nullable=False`** instead, autogenerate still emits
  a plain `add_column(..., nullable=False)`, which will fail against a table that
  already has rows (no default to backfill existing rows with). You'd need to
  add a server default or a manual backfill step yourself, e.g.:
  ```python
  op.add_column("simulation_tasks", sa.Column("priority", sa.Integer(), nullable=False, server_default="0"))
  op.alter_column("simulation_tasks", "priority", server_default=None)  # drop the default once backfilled
  ```
- Don't forget to add the corresponding field to the DTO this table round-trips
  through (`SimulationTaskRow.column_map`/`from_dto`/`to_dto`, or the mixin
  equivalent for other tables) -- Alembic only knows about the database column,
  not your Python-side read/write mapping.

## Worked example 2: adding a brand-new table

Say you're adding a new `widgets` table. Create the model module, e.g.
`llm_d_bench/db/models/widget.py`:

```python
from __future__ import annotations

from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

from llm_d_bench.db.base import Base


class WidgetRow(Base):
    __tablename__ = "widgets"

    id: Mapped[str] = mapped_column(String(36), primary_key=True)
    name: Mapped[str] = mapped_column(String(200), nullable=False)
```

Then register it so `Base.metadata` actually knows about it -- add an import line
to **both** places that build the metadata from scratch (`env.py` for
autogenerate/migrations, and the root `conftest.py` for tests):

```python
# llm_d_bench/db/migrations/env.py
from llm_d_bench.db.models import widget as _widget_model  # noqa: F401
```

```python
# conftest.py
from llm_d_bench.db.models import widget as _widget_model  # noqa: F401
```

(A new table's DAO under `llm_d_bench/db/dao/` is a separate step -- see
`llm_d_bench/db/dao/README.md` -- not something Alembic is involved in.)

Generate the migration:

```bash
alembic revision --autogenerate -m "create widgets table"
```

This produces (verbatim, from an actual run against this exact model):

```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.create_table(
        "widgets",
        sa.Column("id", sa.String(length=36), nullable=False),
        sa.Column("name", sa.String(length=200), nullable=False),
        sa.PrimaryKeyConstraint("id"),
    )
    # ### end Alembic commands ###


def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_table("widgets")
    # ### end Alembic commands ###
```

This is already correct for a simple standalone table. If your new table has a
foreign key to another table, double-check the generated `sa.ForeignKeyConstraint`
references the right column/`ondelete` behavior -- autogenerate reproduces
whatever the model declares, so get it right on the model first.

## Worked example 3: dropping a table

Say `widgets` is no longer needed. Remove its import from both `env.py` and
`conftest.py` (the reverse of example 2) and delete the model module
(`llm_d_bench/db/models/widget.py`). You do **not** need to touch anything else
in Python for the drop itself.

Generate the migration:

```bash
alembic revision --autogenerate -m "drop widgets table"
```

This produces (verbatim, from an actual run against this exact change):

```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_table("widgets")
    # ### end Alembic commands ###


def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.create_table(
        "widgets",
        sa.Column("id", sa.VARCHAR(length=36), autoincrement=False, nullable=False),
        sa.Column("name", sa.VARCHAR(length=200), autoincrement=False, nullable=False),
        sa.PrimaryKeyConstraint("id", name=op.f("widgets_pkey")),
    )
    # ### end Alembic commands ###
```

**This is the one case where you should stop and think before running
`alembic upgrade head`**: dropping a table is destructive and irreversible in
practice (the `downgrade()` recreates the empty table shape, but not the data
that was in it). Before applying:

- Make sure nothing in the codebase still reads/writes this table (search for its
  DAO and any remaining imports of its `*Row`/DTO classes and remove them first).
- If there's any chance you'll need the data later, take a backup/export of the
  table's contents before running the migration, independent of Alembic.

## Things autogenerate gets wrong (review every generated script)

Autogenerate is a diffing tool, not a mind-reader. In all three examples above
the generated script was correct as-is, but that won't always be true:

- A column **rename** is detected as "drop old column + add new column" (silent
  data loss) unless you rewrite it by hand as
  `op.alter_column('table', 'old_name', new_column_name='new_name')`.
- It never generates a **data migration** -- backfilling a new `NOT NULL` column
  on a table that already has rows, converting data from one shape to another,
  etc. is on you to add to the same script.
- Some PostgreSQL-specific constructs -- our `JSONVariant`/`ArrayVariant` portable
  column types, `CHECK` constraints, and certain server-side defaults -- aren't
  always reproduced faithfully. Read the generated DDL and compare it against
  what you actually intended.
- The `downgrade()` half is your responsibility to make correct/safe -- as seen
  above, autogenerate's default `downgrade()` for a dropped table only restores
  the empty shape, never the data.

## Other useful commands

```bash
alembic current                 # which revision is this database on?
alembic history                 # list the full revision chain
alembic upgrade head            # apply all pending migrations
alembic downgrade -1            # revert the most recently applied migration
alembic downgrade <revision>    # revert to a specific point in history
```

Every command above resolves the database URL the same way the application
does, so point your environment (`LLM_D_BENCH_DB_MODE`, `LLM_D_BENCH_DATABASE_URL`,
etc.) at the environment you actually mean to migrate before running one --
there's no separate "migrations database" concept here.

## What NOT to do

- Don't hand-edit `versions/` files that have already been applied to any
  shared/deployed database -- once a migration has shipped, any further change
  must be a *new* migration, not an edit to history.
- Don't delete or renumber existing files in `versions/` -- the chain is linked
  by each script's `revision`/`down_revision` pair, not by filename or order on
  disk.
- Don't run `Base.metadata.create_all()` against a database that already has
  real data in it as a substitute for a migration -- it silently does nothing
  useful there (see above) and can mask a schema drift you actually needed to
  fix.
- Don't skip the review step -- this is the single most common source of
  migration bugs with Alembic in any project, not just this one.

## Testing

The test suite intentionally does **not** run these migrations -- it builds a
fresh in-memory SQLite database per test via `Base.metadata.create_all()` (see
root `conftest.py`), which always reflects the current models, not the migration
history. If you want to sanity-check a migration itself (rather than just the
resulting schema), run it against a scratch PostgreSQL database (e.g. an
embedded instance via `pgserver`) and confirm `alembic upgrade head` /
`alembic downgrade -1` both succeed cleanly.
