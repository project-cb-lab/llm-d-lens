# Prism Code Quality, Module Coupling, and API Consolidation Assessment

## 1. Scope and findings

Remediation tasks are organized by page and capability: Section 2 identifies logic to consolidate, caller migrations, and acceptance criteria for each page; Section 3 inventories API implementations, necessity, and naming recommendations; Section 4 defines API contracts and their maintenance locations.

The scan covers 393 supported production source files under `src/`, `server/`, `llm_d_bench/`, `tools/`, and `scripts/`. `dist/`, dependencies, runtime data, and generated MCP source are excluded from implementation counts.

**Remediation focuses on adopting shared capabilities, aligning business rules, and fixing caller boundaries.** Similar fragments include logic that can be consolidated, callers already using shared components, and domain definitions that should remain separate. Code remediation has not yet been performed; all tasks are recommendations awaiting implementation.

## 2. Remediation tasks by page and capability

The source scan reports **1.10%** textual duplication and **3.90%** structural similarity after ignoring variable names and constants.

**Each page has one remediation task below.** Tables identify business logic to consolidate, its maintenance owner, and differences to retain. Other risks and acceptance criteria appear in the same subsection. Capabilities used by multiple pages are grouped at the end so each page can reuse them.

When business rules, input/output meaning, and lifecycles match, consolidate them under one maintenance owner and migrate callers. When only individual steps match, share those steps; retain separate resource ownership, metric units, and termination behavior. Page code already calling shared components, imports, state declarations, and DTOs from different domains do not need another abstraction merely because they look similar.

## 4. API contracts and maintenance locations

### 4.1 Contract requirements

The following describes the target API contract. Prioritize compatibility adapters and error definitions; migrate paths, fields, and response envelopes gradually through versioning or adapters.

| Area | Current problem | Recommended contract | Treatment of existing endpoints |
|---|---|---|---|
| Paths/versions | /api, /api/v1, and legacy compatibility paths coexist | One canonical entry point per resource; new business APIs use /api/v1/<resource>; nested resources express ownership | Migrate through compatibility forwarding and maintain a canonical-path map rather than forcing all paths to change at once |
| Method semantics | GET cluster/session creates sessions | GET reads without creating/changing business resources; POST creates or triggers actions; PATCH partially updates; DELETE follows its declared contract | Add explicit session-connect/create POST endpoints; migrate the old GET compatibly; fix MCP risk declarations first |
| Parameters | dict/manual conversion and MCP/REST field drift | Request models declare types, required fields, defaults, enums, bounds, and nullability; root-body placement and media types remain consistent | Reuse Pydantic and existing Zod; reject unsupported generated schemas or provide explicit adapters |
| List responses | Arrays, items, and custom envelopes coexist | New lists use {items,next_cursor?}, support filters/pagination, and define stable ordering; individual objects have explicit DTOs | Adapt in domain clients first; migrate historical array contracts individually |
| Status codes | Node often fixes responses at 200; asynchronous operations differ | Read/synchronous success: 200; creation: 201; asynchronous acceptance: 202 plus operation/run ID; no content: 204 | Adjust deployment/installation/task creation according to actual execution behavior while supporting existing consumers |
| Errors | HTTPValidationError documentation differs from actual ProblemDetails | REST uses application/problem+json with type/status/title/detail/code; field errors use a separate errors array; codes remain stable while text may change | Fix 422 declarations first; adapt Node middleware and clients; SSE/JSON-RPC retain their protocols |
| Asynchronous operations | queued/running/ready/succeeded have mixed meanings | Each domain defines its state machine, terminal states, and allowed actions; responses provide operation/run/execution IDs | Preserve the distinction between deployment ready and benchmark succeeded |
| Retries/idempotency | Monitoring APIs have an idempotency header that MCP does not forward | Actions that can create duplicate resources define Idempotency-Key semantics; retries of the same operation reuse the key | First ensure both installation APIs forward the key throughout MCP → Node → Python |
| Cancellation/deletion | HTTP disconnection does not stop background tasks; borrowed resources must be protected | Explicit cancel stops business execution; disconnection cancels only the request/cancelable generation; record deletion and resource cleanup have distinct contracts | Retain owned/borrowed checks; cancellation/cleanup failures return recoverable state |
| Files/uploads/SSE | ZIP parsed as text, filename headers lost, multipart not generated | Multipart preserves boundaries and files; downloads preserve bytes, media type, and filename; SSE defines events and error-termination order | Use separate adapters; do not apply res.json or res.text to all media types |
| Time/naming | Scattered camelCase/snake_case and time fields | Network DTOs are consistent within a domain; timestamps use ISO8601 with time zones; clients map JavaScript fields | Preserve published fields; follow conventions for new fields rather than renaming the entire project |
| Documentation/MCP | --check only proves generated-file freshness | Verify route → OpenAPI → MCP input → actual HTTP request/response together | Add contract tests for multipart, nullable bodies, binary data, headers, and action risks |

Recommended REST error example:

```json
{
  "type": "about:blank",
  "status": 409,
  "title": "Resource is in use",
  "detail": "This storage volume is still referenced by a deployment",
  "code": "storage_volume_in_use"
}
```

Use code for programmatic decisions and detail for explanations; add an errors array when field-level errors are needed. Adapt existing object-valued detail responses compatibly before changing the backend so clients retain the reason. Do not force MCP JSON-RPC or active SSE streams into this HTTP envelope.
