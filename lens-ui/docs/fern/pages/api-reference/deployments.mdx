When specifying an operator preference for deployment planning, use English, such as
`prefer prefix cache`, `more GPU for performance`, or `use fewer GPU resources`.
The deterministic planner matches English preference keywords; Chinese keyword aliases
are no longer supported.

## Backend API

Agentic create and refinement streams use `llm_d_bench.agentic.streaming.planning_stream_response`. The routes retain principal resolution, expected-error classification, and their existing generic error messages. Streams emit `progress` followed by `complete` or `error`; disconnect cleanup cancels and awaits unfinished planning. Gateway operation/log streams remain separate.

Deployments live under the FastAPI router in `llm_d_bench/deploy/router.py` with the `/api/v1/deployments` prefix.

Optimized and precise routing capability metadata reuse `shared_prefix_routing_workload()` in `llm_d_bench.deploy.capabilities`. Each scenario and recommended workload receives independent nested values; provider-specific baselines and goals are unchanged. Precise-provider calibration and model discovery share lazy modelserver invocation traversal while retaining their respective last-value and first-model selection rules.

Agentic candidate generation requires its first tool batch to contain exactly
`get_cluster_overview` and `search_candidates`. An invalid first batch is not executed;
the generator gives the AI one corrective retry before using built-in candidates. If
the retry also violates the tool contract, the fallback is reported as an invalid
generator response rather than a provider connectivity failure. A tool-call limit
failure retains the round, observed call count, and limit in
`generator_fallback_detail` on the run and `generator.fallback_detail` in its
planning snapshot; `generator_fallback_reason` remains the stable category.

Agentic planning estimates missing exact AIC predictions separately for each validated baseline-vllm,
optimized-baseline, and pd-disaggregation candidate using its workload and GPU topology. The
candidate's estimate is supplied to AI scoring as `aic_estimate`; an unavailable estimate remains
unknown, not a performance or SLO guarantee. Agentic estimates do not pass the original search
TTFT/TPOT targets; they verify the fixed topology and workload without an SLO filter. Generator
fallback also estimates the top three built-in candidates, using the resolved workload when the
failed generator left no tool trace. Unsupported or unavailable topologies remain unknown. Relaxed AIC
search accepts complete configurations using no more than the available GPU budget. Its predictions
do not establish compliance with the original SLO. Agentic preserves the relaxed anchor as a
validated candidate even when the generator suggests only a smaller topology, then estimates its
exact topology and workload. Candidates with known estimates that miss the original latency targets
are marked `not_satisfied`; among comparable misses, smaller relative target violations rank ahead
of GPU savings. Unknown estimates are not treated as failures.
When an external planner scores multiple candidates, its selection rationale explains why each
lower-scored returned candidate ranks below the top choice using the supplied planning facts. Only
the returned top three are scored; no reason is inferred for candidates outside that set.

### Estimate an AIC topology

<Tabs>
  <Tab title="REST API">
    **`POST /api/v1/aic/estimate`**

    Send `model_name`, `scenario` (`inference_scheduling` or `pd_disaggregation`),
    `gpu_count`, `mean_input_tokens`, `mean_output_tokens`, the AIC system/backend/database
    and the topology fields (`tp` and `replicas`, or prefill/decode TP and replicas).
    Optional `ttft_target_ms` and `tpot_target_ms` retain the constrained experiment path;
    omit both to estimate the fixed topology without an SLO filter.

    ```json
    {
      "model_name": "Qwen/Qwen3-0.6B",
      "scenario": "inference_scheduling",
      "gpu_count": 1,
      "mean_input_tokens": 1024,
      "mean_output_tokens": 256,
      "aic_system_name": "b60",
      "aic_backend_name": "vllm",
      "aic_database_mode": "SILICON",
      "tp": 1,
      "replicas": 1
    }
    ```

    The response includes `mode`, topology fields, `ttft_ms`, `tpot_ms` and
    `throughput_tokens_per_sec` when measurable. Estimates do not prove SLO compliance.
  </Tab>
  <Tab title="Python API">
    ```python
    from llm_d_bench.aic.models import AICEstimateRequest
    from llm_d_bench.aic.service import estimate

    result = await estimate(AICEstimateRequest(
        model_name="Qwen/Qwen3-0.6B", scenario="inference_scheduling",
        gpu_count=1, mean_input_tokens=1024, mean_output_tokens=256,
        aic_system_name="b60", aic_backend_name="vllm", tp=1, replicas=1,
    ))
    ```

import asyncio

from llm_d_bench.deploy.application import deployment_run_manager
from llm_d_bench.deploy.contracts import DeploymentRunCreateRequest
from llm_d_bench.deploy.standard_kubernetes_service import (
    StandardKubernetesServiceRequest,
    build_standard_kubernetes_service_configuration,
)


async def main() -> None:
    request = StandardKubernetesServiceRequest(
        model="Qwen/Qwen3-8B",
        deployment_name="qwen3-standard",
        description="Standard baseline for smoke tests",
        cluster_session_id="123e4567-e89b-12d3-a456-426614174000",
        replicas=1,
        tensor_parallel_size=1,
    )
    configuration = build_standard_kubernetes_service_configuration(request)
    run = await deployment_run_manager.start_run(
        DeploymentRunCreateRequest(
            configurations=[configuration],
            provenance={
                "deployment_source": {"kind": "standard-kubernetes-service"},
                "cluster_session_id": request.cluster_session_id,
                "deployment_name": request.deployment_name,
                "description": request.description.strip(),
            },
        )
    )
    print(run.id, run.status)


asyncio.run(main())

## Configuration preparation APIs

These Configuration-domain routes prepare artifacts for Deployments and Evaluation. Request and response models live in `llm_d_bench.configuration.models`. The examples use illustrative cluster/session IDs and guide commits; replace them with an active cluster session and real rendered guide provenance. Saving publishes an artifact; rendering alone does not deploy it.

The HTTP boundary uses `application/problem+json` errors. Shared `DomainError` instances retain their original status and code (for example a conflict remains 409); they are not converted into an operation-specific 500. Python service calls raise their original exceptions; the route adapters in `llm_d_bench.configuration.router` apply the HTTP mappings below.

### Revoke deployment access

Remove a user or group share from the deployment resource the caller is authorized to manage.
A binding belonging to another resource or cluster, a global/cluster role binding, or an unknown binding returns `404` without removing it. Existing creator/maintainer share permissions still apply.

<Tabs>
  <Tab title="REST API">

**`DELETE /api/v1/deployments/executions/{execution_id}/access/{binding_id}`**

**`DELETE /api/v1/deployments/runs/{run_id}/access/{binding_id}`**

No request body. Success: HTTP `204` with an empty body. For a missing or mismatched binding, the problem response contains:

```json
{"type":"about:blank","title":"Domain request failed","status":404,"detail":"binding not found","code":"not_found"}
```
  </Tab>
  <Tab title="Python API">

For trusted server code, first authorize the resource and obtain its identity and cluster from the stored deployment. Then call the shared service with that scope:

```python
from llm_d_bench.auth.service import default_service

def revoke_execution_share(binding_id: str, execution_id: str, cluster_id: str) -> None:
    # The caller has already authorized this stored execution.
    default_service().revoke_resource_share(
        binding_id,
        resource_type="deployment_execution",
        resource_id=execution_id,
        cluster_id=cluster_id,
    )
```

For a run, pass `resource_type="deployment_run"`, its run ID, and the cluster ID from its stored provenance. The service validates binding ownership; route-level permission checks remain mandatory.
