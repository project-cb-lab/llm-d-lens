Use the Clusters workflow to register kubeconfig-backed clusters, bootstrap new clusters, review cluster health, and reach the deployments running on each cluster.

## Register a cluster from a kubeconfig

1. Open **Clusters** and click **Add**.
2. In **Add a Kubernetes cluster**, stay on **Basic Info** and enter **Cluster name**.
3. Optionally fill in **Description**.
4. Under **Kubeconfig file**, keep **I already have a kubeconfig**, then click **Browse** and choose the kubeconfig file.
5. Click **Next**. Lens reaches the cluster with the kubeconfig and checks its Kubernetes server version against the minimum pinned by this Lens release (the stack profile's `min_k8s_version`); if the cluster is unreachable or too old, it stays on **Basic Info** and shows why. Otherwise it moves to **Network Proxy**. Choose **Auto-detect this cluster's proxy (recommended)** or **Custom proxy for this cluster**.
6. If you choose **Custom proxy for this cluster**, fill in **HTTP_PROXY**, **HTTPS_PROXY**, and **NO_PROXY**.
7. Continue with **Next** to **Model gateway** and choose the **Provider** (Envoy AI Gateway, Istio, agentgateway, or GKE Gateway) — it is installed once for the whole cluster and model services publish routes against it. On the same **Model gateway** step, set the **Gateway exposed port (NodePort)**, the **Gateway host/IP** (optional; the externally reachable host/IP clients call to reach the Gateway — Lens combines it with the exposed port; leave empty and Lens derives one from the exposed port and the cluster node), the **Lens address** (host/IP; auto-filled with this Lens backend's address — Lens adds its own port, the cluster uses it to check callers; leave empty and Lens fills it in), and the **Node inotify limit** (`fs.inotify.max_user_instances`, default 8192; applied to every node so a busy node does not run out of inotify). Then continue to **Accelerator**, where you select every accelerator the cluster hosts (a heterogeneous cluster selects several) and the driver access mode(s); Lens checks each on the cluster and installs the driver/device plugin from the vendor's upstream manifests when missing, showing per-selection progress. Then **llm-d stack** lists the component versions this Lens release installs (fixed, not editable) — including only the model-server image for the accelerators you selected; clicking **Next** downloads the matching llm-d and llm-d-benchmark sources and pre-pulls the llm-d-router, Inference Payload Processor, gateway-provider and model-server images for the accelerators you selected (a privileged DaemonSet runs `crictl pull` on every node), showing per-image progress before advancing to **Model Cache**.
8. On the last wizard step, click **Review**, then click **Finish**.
9. When the wizard completes, click **Done**.

## Model gateway prerequisites

The shared Gateway is installed once per cluster, but the cluster itself must meet a few
requirements first:

- **Gateway API + Gateway API Inference Extension CRDs** (the `InferencePool` resource,
  `inference.networking.k8s.io/v1`).
- **The chosen provider must be installed.** For the default **Envoy AI Gateway**, install
  Envoy Gateway with the inference-pool addon, otherwise model routes stay
  `ResolvedRefs=False` (`InvalidKind`) and requests return 500:

  ```bash
  helm upgrade -i eg oci://docker.io/envoyproxy/gateway-helm \
    --version v1.8.1 -n envoy-gateway-system --create-namespace \
    -f https://raw.githubusercontent.com/envoyproxy/ai-gateway/v0.7.0/manifests/envoy-gateway-values.yaml \
    -f https://raw.githubusercontent.com/envoyproxy/ai-gateway/v0.7.0/examples/inference-pool/envoy-gateway-values-addon.yaml
  ```

- **A LoadBalancer address must be assignable.** Until the Gateway Service gets an
  `EXTERNAL-IP`, the Gateway shows `Programmed=False` (`AddressNotAssigned`). Cloud clusters
  provide this; local kind clusters need `cloud-provider-kind` or MetalLB. If you cannot add a
  load balancer, set `LENS_GATEWAY_SERVICE_TYPE=NodePort` so Lens renders an `EnvoyProxy` that
  uses a NodePort Service instead.

## Bootstrap a new cluster via Kubespray

1. Open **Add a Kubernetes cluster**.
2. In **Basic Info**, under **Kubeconfig file**, choose **Bootstrap a new cluster via Kubespray**.
3. In the bootstrap panel, fill in **Host(s)**, **Port**, **Role(s)**, **Username**, and either **SSH private key** or **or SSH password** for each node.
4. Click **Add node** for every extra machine you want to include.
5. Under **Network proxy for target nodes**, choose **Auto (reuse whatever proxy is already configured on each target node itself)** or **Custom for these nodes**.
6. If you choose **Custom for these nodes**, fill in **HTTP_PROXY**, **HTTPS_PROXY**, and **NO_PROXY**.
7. Click **Run preflight** and wait for **Preflight results** to show every host as passed.
8. Click **Start bootstrap**.
9. After the generated kubeconfig is returned to the wizard, continue with **Next**, **Review**, and **Finish** to save the cluster in Prism.

## Edit a cluster

1. Select the cluster you want to change.
2. Click **Edit cluster** in the page header, or open the row **Actions** menu and choose **Edit cluster**.
3. In **Edit cluster**, update **Name**, **Description**, **Network proxy**, **Model gateway provider**, **Gateway exposed port**, **Gateway host/IP**, **Lens address**, or **Node inotify limit**. (llm-d component versions are fixed by the Lens release and shown read-only in the create wizard.)
4. If you choose **Custom**, fill in **HTTP_PROXY**, **HTTPS_PROXY**, and **NO_PROXY**.
5. Click **Save changes**.

## Delete a cluster registration

1. Open the cluster's **Actions** menu.
2. Choose **Delete cluster**.
3. In **Delete cluster**, verify that you are removing the correct cluster registration.
4. Click **Delete**.

## Review cluster health and deployment access

1. Select a cluster from the **Clusters** list.
2. Review the summary cards **Workers**, **CPU**, **Memory**, **Deployable GPU**, **VRAM**, **Disk**, and **Monitoring**.
3. In **Deployments**, use **Copy namespace** to copy a deployment namespace.
4. Use **Copy endpoint** to copy the deployment endpoint.
5. If the row shows a local-forward action, click **Open a local port-forward to this deployment**.
6. Open the deployment **Monitoring** menu when you need **Open Grafana**, **Open Prometheus**, or **Profiling**.

## View pods and logs for a deployment

1. Open the deployment you want to inspect and click **View Pods & Logs**.
2. In the drawer titled **Pods & Logs —** followed by the deployment name, review the **Pods** section.
3. Use **All Nodes (`<count>`)**, **Search node...**, or **Search pods...** to narrow the pod list.
4. Click the pod you want to inspect so the log panel shows **Pod Logs:** followed by the pod name.
5. Choose how much history to load with **100 lines**, **200 lines**, **500 lines**, or **1000 lines**.
6. Turn **Previous** or **Auto-refresh (5s)** on or off as needed.
7. Use **Filter log lines...** to narrow the output, or click **Copy** to copy the current log text.

## Delete a deployment and optionally delete its namespace

1. Open the delete action for the deployment so the **Delete deployment** dialog appears.
2. Review **Execution ID**, **Cluster**, and **Namespace**.
3. Leave **Also delete the Kubernetes namespace** checked if Prism should remove the namespace and its resources, or clear it if you only want to remove the deployment record.
4. In the confirmation field labeled **Type** followed by the required phrase and **to confirm**, enter the exact phrase shown in the dialog.
5. Click **Delete deployment**.

## Cluster scoping

Cluster access is scope-aware across Prism. Admins can see and manage every cluster, while maintainers only see the clusters assigned to them; see [Auth and RBAC](/architecture) for the permission model.

## Software preparation consistency

Creating and editing a cluster use the same source-download workflow. Progress covers both llm-d and llm-d-benchmark; terminal failures include each failed repository's reason. A missing returned path preserves its saved value. Creation and editing retain their existing conditions for starting downloads and their own navigation.
